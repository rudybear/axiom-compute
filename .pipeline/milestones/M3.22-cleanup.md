## 1. THE SUBSTITUTION-vs-PARSER SURFACE FINDING (item (a) — read this first; it determines the design)

### 1.1 How holes actually resolve in M3.21

Hole resolution is **whole-source TEXTUAL pre-substitution**, not an HIR rewrite of the parsed tree. `substitute_strategy_holes` (axc-driver `lib.rs:488`, boundary-safe scan from M3.21 F1) replaces every `?name` occurrence in the raw source bytes with the winning integer **before the compile parse**. The compile entry `compile_source_with_assignments_kernel` (`lib.rs:407`) does `substitute_strategy_holes(source, assignments)` at `lib.rs:417`, **then** lexes/parses/lowers/codegens the substituted text.

**Consequence:** on the compile path, `shared[i32,?WG]` with `{WG=64}` becomes the literal text `shared[i32,64]` *before the parser ever sees it*. It flows through the **existing** `IntLiteral` branch of `parse_shared_len` with zero involvement of any hole machinery. The parser gap **does not bite the compile path** — this is exactly why `matmul_shared_f32.axc` has always worked (M3.21's own deviation comment, `two_pass_reduce.axc:9-21`, records this).

### 1.2 Where the gap DOES bite: the hole-DISCOVERY parse (and verify)

The parser gap bites the flows that parse the **RAW, unsubstituted** source:

1. **Hole discovery (the enumerator path).** `run_optimize` (`optimize.rs:87`) calls `parse(&source)` on the **raw** file to run the lexer/parser/HIR pipeline and `union_module_holes` to discover every `@strategy` hole. If the raw file contains `shared[i32,?WG]`, `parse_shared_len` (`parser.rs:1331`) rejects `?WG` (an `OptHole` token, not `IntLiteral`) with `SharedSizeMustBeUnsuffixedPositiveIntegerLiteral` — **the entire optimize run aborts at parse, before a single hole is discovered.** This is the confirmed-on-main failure.
2. **Module-wide cross-validate re-parse** (`optimize.rs:188`, F4) and **rewrite-verify** — any consumer that re-parses raw (pre-substitution) source containing a shared-len hole.
3. **`@workgroup(?WG,…)` parses fine on the raw source** (annotation-arg parser accepts `OptHole` → `AnnotationArg::HoleRef`, `parser.rs:950`), which is *why* M3.21 could keep `?WG` in `@workgroup` while being forced to use a literal `64` in `shared[…]`. The asymmetry is entirely in the type/decl grammar, not the annotation grammar.

**Item (a)'s real job is therefore NARROW:** make the parser *accept* `?WG` in shared-length position so the **raw source is a valid AST for discovery**. The hole value is resolved by one of two downstream mechanisms (textual substitution OR the enumerator HIR rewrite, §1.2b); codegen never needs to consume a hole-valued shared length on the happy path. This finding shrinks the milestone: no HIR→codegen hole-length plumbing is required — only "carry the hole far enough that discovery succeeds, resolve it to a literal at either resolution point, and fail closed if a hole ever reaches codegen."

### 1.2b The TWO entry points, and which one resolves the hole how (r3 — HIGH fix, verified against source)

There are **TWO** places a shared-len hole gets resolved to a literal before codegen. **Both were verified in source at r3** (`optimize.rs`, `bench_variant.rs`, `mcp/tools/grid_search.rs`). r2 mis-stated which path the MCP tools use; this is the corrected map:

1. **TEXTUAL path (already works today; the fix is not needed here).** `substitute_strategy_holes` replaces every `?name` in the raw bytes *before* parse, so `shared[i32,?WG]` is the literal `shared[i32,64]` at the parser (§1.1). **Three production consumers ride this path, all textual:**
   - `axc compile` / `compile_source_with_assignments_kernel` (`lib.rs:407`) — the restored M3.21 GPU test `dispatch_two_pass_reduce.rs` (AT-2977).
   - **MCP `bench_variant`** (`mcp/tools/bench_variant.rs:234`) — resolves each variant via `compile_source_with_assignments_kernel`, then GENUINELY dispatches on the GPU (`vk.prepare_kernel` → `vk.dispatch_handle`, `bench_variant.rs:~283/~296`) and runs the correctness oracle (`check_correctness`).
   - **MCP `grid_search`** (`mcp/tools/grid_search.rs:307-321`) — enumerates variants and, per variant, calls `bench_variant::handle` (textual). **It NEVER calls `resolve_single_variant` or `emit_module`.**

   Because all three are textual, the parser fix (item (a)) alone unblocks them: once the raw source *parses* (so discovery/`union_module_holes` succeeds), `?WG` is substituted to a literal before codegen. **The MCP `grid_search` tool already benchmarks shared-len variants FOR REAL** (real dispatch + real timings + correctness oracle on Lavapipe) the moment the parser accepts `?WG`.

2. **NON-TEXTUAL path — the ONLY consumer of `resolve_single_variant`, and the ONLY reason the fix exists.** `run_optimize` (`optimize.rs:87`) → the library `axc_optimize::grid_search` → `resolve_single_variant` (`enumerator.rs:145`) → `emit_module` (`grid_search.rs:201`). This resolves each variant **at the HIR level**: `resolve_single_variant` rewrites `@workgroup` dims and clones the body **verbatim** (`body: kernel.body.clone()`, `enumerator.rs:191`), `strategy=None`. A shared decl carrying `len_hole=Some("WG")` (placeholder `SharedTy.len=1`) is cloned **unsubstituted** into every variant, so the new `CodegenError::UnresolvedSharedLenHole` backstop (§1.3) fires on EVERY variant → `grid_search` returns `NoSuccessfulVariants` → **`axc optimize` ERRORS out**. That is the whole bug the `~15` LOC fix repairs.

**The honest, bounded payoff of the `resolve_single_variant` fix — stated exactly (r3 downgrade of the r2 headline):** WITHOUT it, a shared-len hole makes `axc optimize` **fail-closed** (`NoSuccessfulVariants`). WITH it, `run_optimize` **completes** and writes a winner. That is the entire deliverable of the fix, and it is genuine and worth doing. It does **NOT** mean `run_optimize` "truly benchmarks" the variants: `run_optimize`'s bench is a **MOCK** (a fixed `1000ns` for every variant, `optimize.rs:127-134`) and it passes `correctness_fn = None` to `grid_search`, so on this path **no variant is dispatched and no correctness is checked** — the "winner" is ordinal-0 by tie, independent of shared-tile size (a **pre-existing** M2.3 limitation, honestly noted, not introduced or fixed here). The real per-variant shared-tile *benchmarking* lives on the TEXTUAL MCP `grid_search` path (entry 1). Note also that `run_optimize` compiles its final winner artifact **textually** (`compile_source_with_assignments_kernel`, `optimize.rs:~157`, after a `substitute_strategy_holes` cross-validate), so the `.spv` it writes has `?WG` resolved textually in **both** `@workgroup` and `shared` — the winner artifact is internally consistent regardless of the mock timing.

**The `~15`-LOC fix in `resolve_single_variant` (UNCHANGED from r2):**

- After building the resolved kernel, if `body` is `KernelBody::Typed`, iterate `body.shared` (`expr.rs:411`, `Vec<SharedDecl>`). For each `SharedDecl` with `len_hole == Some(name)`:
  - look up `assignments.values.get(name)`; **substitute by the hole's OWN name** (unlike `@workgroup`, which keys on the `workgroup_x/y/z` convention — the shared-len hole name IS its assignment key, e.g. `"WG"`).
  - if present and `> 0`: set `decl.ty.len = value as u32` and clear `decl.len_hole = None`. `SharedTy.len` stays `u32` — the resolved variant clone holds a concrete literal, exactly like the textual path.
  - if the name is absent from `assignments` (typo'd / undeclared reference): **leave `len_hole = Some(..)` untouched** — the `emit_module` backstop then fails that one variant closed (fail-closed), never sizing an array from the placeholder `1`.
- No change to `SharedTy` (`u32` preserved), no change to codegen, no golden perturbation.

**Scope of `resolve_single_variant` — SINGLE benched kernel only (r3 — folds MEDIUM #2).** `grid_search` wraps exactly one resolved kernel into a module (`HirModule { kernels: vec![resolved] }`, `grid_search.rs:200`), and `run_optimize` benches only the `select_kernel`-chosen kernel. On a 2-kernel source (e.g. `two_pass_reduce`, both kernels `shared[i32,?WG]`), the SIBLING kernel's shared-len hole is **never seen by `resolve_single_variant`** — it is resolved **textually** by the F4 module-wide cross-validate (`substitute_strategy_holes` → `compile_module_all`, `optimize.rs:~155`) before any output is written. So the fix resolves the *benched* kernel's shared-len hole on the grid-search path; siblings remain textual (F4). It does NOT "walk all kernels' shared decls".

**Known limitation recorded (r3 — the `@workgroup(?WG)` asymmetry).** `resolve_single_variant`'s workgroup resolution is keyed on the `workgroup_x/y/z` *convention* names (`resolve_wg_dim`, `enumerator.rs:163-165,198-213`), NOT on a hole's own name. So a hole named `WG` used in `@workgroup(?WG)` is **NOT** resolved on this HIR path (its dims stay the `(1,1,1)` placeholder) — only the shared-len is resolved by the fix's by-name substitution. This asymmetry is harmless here **because** the non-textual path never dispatches (mock bench) and the winner artifact is compiled textually; it would only bite a hypothetical future real-dispatch consumer of `resolve_single_variant`, which does not exist. Recorded as a defer-list item (§7), not fixed in this cleanup milestone.

So AT-2977 (textual GPU) and the two legs of AT-2984 each exercise a path that genuinely works: Leg A the `run_optimize` completes-without-erroring guarantee, Leg B the textual MCP `grid_search` real dispatch.

### 1.3 The minimal-sound representation (KEY INVARIANT)

**HIR `SharedTy.len` stays `u32`** (`shared.rs:46`). Codegen (`OpTypeArray` needs a concrete constant length), `total_byte_size()`, and every access-chain path are **untouched**. The hole is carried as **additive metadata** so it survives parse→HIR for discovery and can be caught fail-closed at codegen:

- **AST:** `parse_shared_len` returns a small enum `ParsedSharedLen { Lit(u32), Hole(String) }`. `Stmt::SharedDecl` carries the hole additively (recommended: keep `len: Spanned<u32>` as a **placeholder** `1` when a hole is present, and add `len_hole: Option<axc_lexer::Spanned<String>>`; equivalently an enum field — coder's choice, but the placeholder-plus-`Option` form minimizes ripple through existing `Stmt::SharedDecl` consumers). `TypeRef::Shared` (type-position, only reachable where `shared` is ultimately rejected as a param) accepts the hole token to avoid a confusing parse error but need not resolve it precisely.
- **HIR:** `SharedDecl` (`crates/axc-hir/src/shared.rs:105`) gains `len_hole: Option<String>` (additive; fields today are `id`/`name`/`ty`/`span`, with `SharedTy.len: u32` at `shared.rs:46`). When `Some`, `SharedTy.len` holds the placeholder `1`.
- **Aggregate shared-memory check** (the reachable one in `typecheck.rs:1442`): **skip** any kernel whose typed body contains a shared decl with `len_hole.is_some()` (mirrors lower.rs's existing "skip workgroup dim validation when `@workgroup` has holes", `lower.rs:260-263`). Discovery never codegens, so under-counting bytes on a placeholder is harmless there; the compile path always has literals so the check runs normally.
- **Codegen backstop (fail-closed — the soundness guarantee):** add `CodegenError::UnresolvedSharedLenHole { kernel_name, name }` mirroring the existing `UnresolvedStrategyHole` backstop (`emit.rs:128-133`). Before emitting, scan the typed body; if any shared decl still has `len_hole.is_some()`, error. This is required because F2 **strips** the `@strategy` block, so a declared-but-unassigned or typo'd `?WG` in a shared length would otherwise slip past the strategy-hole backstop (which only inspects `kernel.annotations.strategy`) and size an array from the placeholder `1`. This backstop honors the AST contract ("codegen rejects any HIR module that still contains an unresolved `HoleRef`", `ast.rs:159-160`).

### 1.4 GPU proof — restore AT-2956's original intent

Restore the M3.21 deviation: edit `examples/two_pass_reduce.axc` so the shared tiles read `shared[i32, ?WG]` (both kernels) instead of the literal `shared[i32, 64]`, keeping `@strategy { WG: ?[64] }` (single candidate 64). This exercises the full path: raw parse (discovery) → substitution `?WG`→`64` → compile → dispatch. `out[0] == Σ(input)` bit-exact on NVIDIA + Lavapipe (the M3.21 GPU test, now with the shared hole live). Also remove the now-obsolete DEVIATION comment block (`two_pass_reduce.axc:9-21`), replacing it with a one-line note that the shared hole is live as of M3.22.

## 3. Local-array symmetry decision (item (a)): **shared-only; local-array holes explicitly DEFERRED**

`array[T,N]` (M3.20) has the **identical** gap: `parse_local_array_len` (`parser.rs:1505`) also only accepts an `IntLiteral`. The decision is **deliberately asymmetric — fix shared, defer local-array — recorded, not silent:**

**Rationale:**
- **No driving example.** The only use case (AT-2956 / `two_pass_reduce` restoration, hole-tuned shared *workgroup* tiles) is shared. Hole-tuned per-thread local-array register-blocking has no current consumer.
- **M3.20 discipline.** Symmetric plumbing (a second AST type + decl stmt, `parse_local_array_len`, an additive HIR field, a typecheck skip, a codegen backstop) roughly **doubles** the touch-sites of a parser change that requires a corpus golden re-bless — the exact ballooning the M3.20 lesson says to defer.
- **Honesty, not silence.** The asymmetry is recorded as a **new ROADMAP backlog row** ("`array[T,N]` length position does not accept a `HoleRef` — symmetric to the shared gap closed in M3.22; deferred, no driving example; ~120 LOC") so a future reader sees a deliberate deferral, not an oversight.
- **Guarded by a test.** AT-2978 asserts `array[i32,?N]` **still rejects at parse** with a clear error — this pins the deferral and guards against an accidental half-implementation.
