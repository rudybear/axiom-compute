**Architect design spec + execution plan + test requirements.**

## 1. Goal and scope

Extend the proven M2.6 Q4_K_M dequant pattern to two more ggml K-quant formats:

- **Q6_K** — the higher-value target. Real llama.cpp "Q4_K_M" GGUF checkpoints store a
  handful of sensitive tensors (`output.weight`, `attn_v.weight`, and often `attn_k`) in
  **Q6_K**. Without Q6_K dequant, AXIOM cannot run those tensors, so Q6_K closes a real
  coverage hole for the beachhead and the held M4.2 upstream case.
- **Q5_K_M** (ggml `block_q5_K`) — a clean structural extension of Q4_K_M (identical
  superblock scale/min machinery + one extra high bit per weight), and therefore a
  near-verbatim reuse of the M3.6 scale-cached coopmat leader.

**This is a COVERAGE milestone, not a performance milestone.** M3.13 formally concluded the
Q4_K_M throughput campaign (the residual 2.39× on NVIDIA is the portable-coopmat tax). M3.14
adds *correct* dequant for two more formats; it does **NOT** open a new leader-tuning campaign
and asserts **no TFLOPS gate**. The M3.6 scale-cache pattern is reused for Q5_K_M **only
because it drops in near-verbatim**; for Q6_K it does not drop in cleanly (§4.3) and a fused
coopmat Q6_K kernel is explicitly deferred.

### In scope
1. CPU reference dequant oracles for Q6_K and Q5_K_M — byte-exact against the canonical ggml
   layout, following the `q4km_oracle.rs` pattern (pure-dequant + f32-accumulator matmul
   reference + condition-aware combined metric).
2. One **portable** (non-coopmat, Lavapipe-runnable) multi-output dequant+matmul `.axc` kernel
   per format — the M3.1 `q4km_dequant_matmul.axc` pattern — proving dequant correctness
   **bit-exact** (`max_diff == 0`) at K=256 and **combined ≤ 1e-3** at large K.
3. For **Q5_K_M only**: a `q5km_matmul_rb_coopmat_f32acc_cached.axc` kernel — the M3.6 leader
   VERBATIM except (a) the 176-byte block offsets and (b) an extra qh high-bit read that adds
   16 to the nibble. NVIDIA tensor-core path, combined ≤ 1e-3.
4. AT-numbered tests continuing from AT-2811, including CPU oracle-vs-ggml golden tests,
   compile/spirv-val/cap-set anchors, and real-GPU correctness (Lavapipe in CI + NVIDIA).

### Out of scope (explicit)
- **No fused coopmat Q6_K matmul.** Q6_K's signed int8 per-16-element scales and 210-byte
  layout are *not* a clean drop-in for the M3.6 (row×8-sub-block) scale cache (§4.3). The
  portable multi-output Q6_K kernel proves the dequant; a fused Q6_K tensor-core kernel is a
  distinct design deferred to a follow-up if the beachhead demands the fused path.
- **No new leader-tuning / TFLOPS campaign** (M3.13 closed that). No perf gate is asserted.
- **No loosening of the FROZEN 1e-3 tolerance**, ever.
- **No new SPIR-V capability or extension** beyond the Q4_K_M set (§7).
- No i-quant / imatrix formats (IQ4_XS, Q3_K, etc.) — out of this milestone.

## 2. Phasing

**M3.14a = Q6_K first, M3.14b = Q5_K_M second.** Justification:

- Q6_K carries the **only novel risk** in this milestone: signed arithmetic (int8 scales in
  [-128,127] and 6-bit quants biased by −32). AXIOM exposes **no signed-int read or convert
  builtin** (verified §7), so the sign handling must be done pure-source in f32 with a branch.
  Doing the risky format first surfaces any hidden compiler gap early, while the harness is
  fresh, and is the higher-value beachhead target.
- Q5_K_M is the low-risk clean extension (all-unsigned, identical scale machinery to Q4_K_M)
  and additionally inherits the M3.6 coopmat leader with a one-line dequant change, so it lands
  fast once the oracle/test plumbing from M3.14a exists.

(The alternative — Q5_K_M first to validate plumbing cheaply — was considered and rejected:
the plumbing is already proven by Q4_K_M's `q4km_oracle.rs`/tests, so there is no plumbing risk
to de-risk, and value+novel-risk both point to Q6_K first.)

## 3. Canonical layouts (FROZEN — verified against ggml and the repo's Q4_K_M conventions)

The task brief's byte counts were cross-checked against canonical ggml `k_quants` and the
repo's own frozen Q4_K_M layout (`DESIGN.md §3.1.11`, `q4km_oracle.rs`). **The repo/ggml
canonical layout rules where the brief differed** (the brief's "ql[64] + qh[32]" for Q6_K is a
per-128-half slice, not the full-superblock byte counts). The frozen full-superblock layouts:

### 3.1 Q6_K — ggml `block_q6_K`, **210 bytes / 256 weights**
```
offset  size  field
[0..128]  128  ql[128]   low 4 bits of each weight   (QK_K/2 = 128)
[128..192] 64  qh[64]    high 2 bits of each weight  (QK_K/4 = 64)
[192..208] 16  scales[16] int8 (SIGNED) per-16-element scales (QK_K/16 = 16)
[208..210]  2  d         ggml_half super-scale (IEEE-754 binary16 LE)
```
Canonical ggml dequant (the byte-exact oracle spec). The superblock is processed in **2 halves
of 128 weights**; within each half `h ∈ {0,1}`, for `l ∈ 0..32`, `is = l/16`:
```
q1 = ((ql[64h + l]      & 0x0F) | (((qh[32h + l] >> 0) & 3) << 4)) - 32
q2 = ((ql[64h + l + 32] & 0x0F) | (((qh[32h + l] >> 2) & 3) << 4)) - 32
q3 = ((ql[64h + l]      >>  4)  | (((qh[32h + l] >> 4) & 3) << 4)) - 32
q4 = ((ql[64h + l + 32] >>  4)  | (((qh[32h + l] >> 6) & 3) << 4)) - 32
y[128h + l +  0] = d * sc[8h + is + 0] * q1
y[128h + l + 32] = d * sc[8h + is + 2] * q2
y[128h + l + 64] = d * sc[8h + is + 4] * q3
y[128h + l + 96] = d * sc[8h + is + 6] * q4
```
where `sc[·]` is the **signed** int8 scale. `q*` ∈ [-32, 31]; `sc` ∈ [-128, 127].
**NOTE the field ORDER differs from Q4_K_M**: in Q6_K, `d` is the *last* 2 bytes (offset 208),
not the first. There is **no `dmin`** (Q6_K has no per-block min — it is a symmetric,
zero-offset quant; the −32 bias is applied to the quant, and the scale is signed).

### 3.2 Q5_K_M — ggml `block_q5_K` (K_SCALE_SIZE=12 variant), **176 bytes / 256 weights**
```
offset  size  field
[0..2]     2  d         ggml_half super-scale (for the 6-bit scales)
[2..4]     2  dmin      ggml_half super-min  (for the 6-bit mins)
[4..16]   12  scales[12] packed 8×(6-bit scale, 6-bit min) — IDENTICAL to Q4_K_M
[16..48]  32  qh[32]    high bit of each weight (QK_K/8 = 32)
[48..176] 128 qs[128]   low 4 bits of each weight (2 nibbles/byte) — IDENTICAL layout to Q4_K_M qs
```
Q5_K_M is **Q4_K_M plus one high bit per weight**. `d`, `dmin`, the 12-byte packed scales, and
`get_scale_min_k4` are byte-identical to Q4_K_M. The dequant differs ONLY by promoting the
4-bit nibble to a 5-bit value before the multiply:
```
// chunk = k/64 (0..3), l = (k%64)%32 (0..31), is_hi = (k%64)/32 (0=lo,1=hi), is = chunk*2 + is_hi
nib   = (is_hi==0) ? (qs[chunk*32 + l] & 0x0F) : ((qs[chunk*32 + l] >> 4) & 0x0F)
qh_bit_index = 2*chunk + is_hi                       // 0..7
hi    = (qh[l] >> qh_bit_index) & 1                   // 0 or 1
nib5  = nib + hi*16                                   // 0..31, UNSIGNED
y[k]  = d*sc[is] * nib5 - dmin*m[is]                  // SAME multiply-then-subtract as Q4_K_M
```
All-unsigned; the scale/min machinery is verbatim Q4_K_M. This is why the M3.6 coopmat kernel
drops in cleanly (§4.3).

## 4. Kernels

All kernels are **pure source** (zero compiler change). Anti-pattern discipline: explicit
`return;` (#2), no `>>` — use `lshr`/`shr` (#8), explicit types (#1), `k % n` written as
`k - (k/n)*n` (#8).

### 4.1 `examples/q6k_dequant_matmul.axc` (portable, Lavapipe-runnable) — M3.14a
Mirror `examples/q4km_dequant_matmul.axc` (M3.1): `@workgroup(64,1,1)`, one invocation computes
one output `y[row*n_cols + col] = sum_k dequant_q6k(q[row,k]) * x[k,col]`, `x`/`y` are `f32`.
Signature:
```
@kernel @workgroup(64,1,1)
@intent("Multi-row Q6_K dequant + matmul: y[row,col] = sum_k dequant_q6k(q[row,k]) * x[k,col]")
@complexity(O(n))
fn q6k_dequant_matmul(
    q: readonly_buffer[u8],
    x: readonly_buffer[f32],
    y: buffer[f32],
    n_rows: u32,
    n_cols: u32,
    n_blocks_per_row: u32,
) -> void
```
Per-superblock byte base = `row * n_blocks_per_row * 210 + sb * 210`. Field offsets per §3.1
(ql @ +0, qh @ +128, scales @ +192, d @ +208). Walk the ggml half/l structure OR the flat-k
decode; both must reproduce §3.1 exactly.

**Signed handling — pure source, NO new builtin (the one novel technique):**
```
// signed int8 scale from a zero-extended u8 read:
let sc_u: u32 = ptr_read_u8_zext(q, scales_base + sc_index);   // 0..255
let mut sc_f: f32 = f32_from_u32(sc_u);
if sc_u >= 128u32 { sc_f = sc_f - 256.0f32; }                  // now [-128,127] as f32

// signed 6-bit quant (q - 32), computed in f32 (q_u in 0..63 is exact under f32_from_u32):
let q_u: u32 = bor(band(ql_byte, 0x0Fu32), shl(band(lshr(qh_byte, qsh), 3u32), 4u32));  // 0..63
let q_f: f32 = f32_from_u32(q_u) - 32.0f32;                    // [-32,31], exact

let w: f32 = d * sc_f * q_f;
```
The whole path is existing builtins (`ptr_read_u8_zext`, `f32_from_u32`, `band`, `bor`, `shl`,
`lshr`) + f32 arithmetic + an `if`. No signed-int read/convert op is required or added.

**MANDATORY Coder discipline (most transcription-error-prone part):** the kernel source MUST
carry a **line-by-line inline comment** mapping the `sc[8h + is + {0,2,4,6}]` index arithmetic
(and the `q1/q2/q3/q4` reassembly) directly to §3.1's formula lines — the same way
`examples/q4km_dequant_matmul.axc` comments its inlined `get_scale_min_k4`. Whichever loop form
is chosen (ggml's explicit 2-half/`l`/`is` loop OR a flat-k decode), the comment must make the
`h`/`l`/`is` → `sc` mapping auditable against §3.1 without re-deriving it.

### 4.2 `examples/q5k_dequant_matmul.axc` (portable, Lavapipe-runnable) — M3.14b
Mirror `q4km_dequant_matmul.axc` **verbatim** except: block stride 176 (not 144); qs base =
`base + 48`; qh base = `base + 16`; and the nibble→5-bit promotion of §3.2 (`nib5 = nib +
hi*16`). Scale/min decode (`get_scale_min_k4`, `d*sc`, `dmin*m`) is byte-identical to Q4_K_M.
Same signature shape as §4.1 (`q5k_dequant_matmul(q,x,y,n_rows,n_cols,n_blocks_per_row)`).
All-unsigned — no signed technique needed.

### 4.3 `examples/q5km_matmul_rb_coopmat_f32acc_cached.axc` (NVIDIA coopmat) — M3.14b
The **M3.6 leader** (`q4km_matmul_rb_coopmat_f32acc_cached.axc`) reused VERBATIM — same
`@workgroup(32,1,1)`, `@cooperative_matrix`, `@strategy` holes, the two `shared[f32,256]`
`dsc_cache`/`dmm_cache`, the once-per-superblock cooperative fill, the 3-barrier structure, the
4 f32 accumulators, the single-level OpPhi K-carry, and `coopmat_store` — with EXACTLY these
minimal deltas:
1. **Block stride 144 → 176**; scales region stays at `base+4` (get_scale_min_k4 unchanged);
   the qs read base becomes `base + 48` (was `base + 16`); a new `qh` read base `base + 16`.
2. **A-stage per-nibble dequant**: after computing `nib`, read the qh high bit and promote:
   `nib5 = nib + hi*16` (per §3.2), then `w = f32_to_f16(dsc*f32_from_u32(nib5) - dmm)`. The
   `dsc_cache`/`dmm_cache` FILL is byte-identical to M3.6 (same d/dmin/get_scale_min_k4).
3. Header comment documents it as the M3.6 pattern extended to Q5_K_M; barriers/uniformity
   analysis carries over unchanged (the fill still writes only the caches; the qh read is a
   plain per-element `readonly_buffer[u8]` load in the A-staging loop, no new barrier).

**Why Q6_K does NOT get this treatment (the clean-drop-in test fails):** the M3.6 cache is
sized 256 = 32 rows × **8** sub-blocks (Q4_K_M/Q5_K_M have 8 six-bit scales per superblock).
Q6_K has **16** signed int8 scales per superblock (one per 16 elements) and **no `dmin`/min
cache**, so the cache layout, index arithmetic (`row_local*8+is`), and the fill would all have
to change — that is a *new* fused-kernel design, not a verbatim reuse. Per the milestone's
"reuse only if it drops in cleanly" rule, the Q6_K fused coopmat kernel is deferred; the
portable §4.1 kernel proves Q6_K dequant correctness.

## 5. CPU reference oracles

New public library modules. **Two distinct templates (Coder-facing, do not conflate):**
- The **f32-accum / f16-staged** reference functions (`*_f32accum_cpu`, `*_abs_dot_scale`) and
  the shared metric fns mirror `crates/axc-driver/src/q4km_oracle.rs`.
- The **bit-exact (native-f32, no f16 rounding)** reference `*_dequant_matmul_f32_cpu` mirrors
  the template **`crates/axc-driver/tests/common_matmul.rs::q4km_dequant_matmul_cpu`** — that is
  where the bit-exact path actually lives, **NOT** in `q4km_oracle.rs`. The new oracle modules
  expose this bit-exact fn as a `pub` library fn (so both the driver crate and the dispatch
  tests can call it) while copying `common_matmul.rs`'s exact per-element dequant + accumulation.

**Bit-exactness-by-construction requirement (FROZEN, makes AT-2814/2819 `max_diff==0` safe):**
the CPU bit-exact oracle MUST use the **same floating-point associativity as the kernel** —
weight = `(d * sc_f) * q_f` for Q6_K and `(d*sc) * nib5 - (dmin*m)` for Q5_K_M, in that exact
grouping — matching `common_matmul.rs::q4km_dequant_matmul_cpu`. (The pessimistic review proved
the pure-source sign path is bit-exact-safe: for all `u∈[128,255]`, `f32_from_u32(u) − 256.0`
equals `(i8)u as f32` exactly, and `q_u∈[0,63]` / `sc_u∈[0,255]` convert exactly — so
`max_diff==0` is achievable *by construction*, not by luck, PROVIDED this associativity holds.)

pub fn q6k_dequant_matmul_f32accum_cpu(q: &[u8], x_f16: &[u16], n_rows: usize, n_cols: usize, n_blocks_per_row: usize) -> Vec<f32>;

// where x is native f32. Mirrors tests/common_matmul.rs::q4km_dequant_matmul_cpu (NOT q4km_oracle.rs);

The three slice-only metric functions (`max_rel_diff`, `q*_abs_dot_scale`-consuming

## 6. Acceptance tests (AT-2811 .. AT-2823)

Gate metric discipline (FROZEN, never loosened): **bit-exact `max_diff == 0`** for the
small-K portable-kernel gate (pure dequant, order-matched f32 accumulation over K=256, exactly
as M3.1 AT-1520 achieved for Q4_K_M); **combined condition-aware ≤ 1e-3** (via
`max_rel_diff_combined`) for large-K and for the f16-input coopmat path (exactly as
AT-1780/1800..1802). Both metrics are REPORTED at every size. GPU tests are `#[ignore]`-gated
on `AXC_ENABLE_GPU_TESTS=1`; NVIDIA-coopmat tests typed-skip on Lavapipe
(`CoopMatUnsupported`/`DeviceFeatureUnsupported`) and on `subgroup_size() != 32`. Portable
(non-coopmat) GPU tests are NOT `#[ignore]` — they run on Lavapipe in CI (mirror AT-1520).

**Golden-fixture provenance (AT-2811 / AT-2816) — prefer the stronger option:** the golden
superblock SHOULD be **cross-checked against a real ggml byte dump** (a Q6_K / Q5_K superblock
emitted by `llama.cpp`/`ggml-quantize` and captured as a hardcoded byte array + its
`dequantize_row_q6_K` / `dequantize_row_q5_K` output), NOT merely hand-computed from §3.1/§3.2.
A hand-computed golden only proves the Rust oracle matches the *documented* formula; a real-ggml
dump additionally guards against a transcription error in the frozen layout tables themselves.
If a live ggml dump is impractical in the Coder/QA environment, a hand-computed-from-formula
golden is ACCEPTED as a fallback **provided** it is annotated as such in the test and the byte
array is documented with the exact ggml struct field it represents (so a later ggml cross-check
is a drop-in). QA MUST record which of the two was used.

## 7. Compiler-change flag: **NONE expected**

Verified from `crates/axc-hir/src/q4_0.rs` (the reserved builtin table) and the codegen: the
available Q-format builtins are exactly `ptr_read_u8_zext`, `ptr_read_u16_zext`,
`f16_bits_to_f32`, `f32_from_u32`, `f32_to_f16`, plus bitwise `band/bor/shl/shr/lshr`. There is
**no signed-int read or convert builtin** (`f32_from_i32`, `ptr_read_i8_sext`, etc. do not
exist).

Both formats are nonetheless fully expressible **pure-source**:
- **Q5_K_M** is entirely unsigned (nibble + conditional +16) — trivially existing builtins.
- **Q6_K** signedness is handled in f32 without any signed-int op: the (q−32) bias is
  `f32_from_u32(q_u) − 32.0f32` (q_u∈[0,63] is f32-exact), and the int8 scale is
  `f32_from_u32(sc_u); if sc_u >= 128 { sc_f −= 256.0f32; }` (§4.1). This is the SAME
  technique class as existing kernels (branch + f32 arithmetic).

**Hard requirement for the Coder:** if any hidden gap forces a codegen/HIR/typecheck/parser/
lexer change, STOP and flag it to the Architect (per CLAUDE.md hard-rule #5 / anti-pattern:
Q4_K_M needed zero compiler changes beyond what exists, and Q6_K/Q5_K_M must too). The
AT-2813/2818/2821 "zero-new-builtin + cap-set-identity" anchors are the mechanical guard that
this held.

## 8. Edge cases
- **Q6_K field order**: `d` is the LAST 2 bytes (offset 208), and there is **no `dmin`** — a
  reader copy-pasting the Q4_K_M header (d,dmin first) will mis-decode. Called out in §3.1 and
  the kernel header.
- **Q6_K negative scales / quants**: the `sc_u >= 128` reconstruction and the `−32` bias must
  be present; AT-2811/2812 fixtures include negatives specifically to catch a missing sign path
  (an all-positive fixture would pass a broken unsigned kernel).
- **Q5_K_M qh bit indexing**: `qh_bit_index = 2*chunk + is_hi` (0..7) into `qh[l]` where
  `l = (k%64)%32`; a wrong bit index passes for chunk 0 but fails chunks 1..3 — AT-2816
  exercises all 8 positions.
- **Block-stride constants** (210 / 176) must not be copied as 144; the compile anchors don't
  catch this (it's a runtime index), so AT-2814/2819 use multi-superblock-capable fixtures and
  non-symmetric data.
- **Lavapipe f16**: the portable kernels use `f32` x/y (no coopmat, no f16 SSBO) → run on
  Lavapipe. The Q5 coopmat kernel typed-skips on Lavapipe (`CoopMatUnsupported`), like M3.6.
- **50 GB test-executable limit**: all fixtures are small (K ≤ 2048 for portable, K ≤ 14336 for
  the single coopmat A/B correctness test at M=N=64) — far under the limit.
