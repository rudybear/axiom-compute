## 1. One-paragraph summary

`array[T, N]` is a per-invocation (thread-private) sized array declared in a kernel
body, allocated as a **Function-storage** `OpVariable` of `OpTypeArray %elem %N`,
read/written via a single-index `OpAccessChain` + `OpLoad`/`OpStore`. It is the
**private-memory sibling of `shared[T, N]` (FG.6, M3.2)** — the entire pipeline
(lexer keyword → parser `TypeRef::LocalArray` + `Stmt::LocalArrayDecl` → HIR
`LocalArrayId`/`LocalArrayTy`/`LocalArrayDecl` + `LocalArrayRead`/`LocalArrayWrite` →
codegen `OpTypeArray`/`OpVariable Function`/single-index `OpAccessChain`) mirrors
`shared` **with two deliberate divergences**: (a) **Function** storage class instead of
**Workgroup**, so the `OpVariable` is emitted in the function **entry-block prelude**
(exactly like `let` scalars, the M3.11 carry pattern) rather than in the module globals
section; and (b) **no runtime metadata / preflight** — private memory is not a
device-limited resource, so the `metadata` schema stays at its **current version (v4,
`CURRENT_SCHEMA_VERSION = 4` at `metadata.rs:194`)** unchanged, adding no field (a
golden-identity win). *(r2: corrected from "v3" — the schema was bumped to v4 at M3.17; the
substantive claim "no bump, local arrays are metadata-inert" is unchanged.)* This unlocks per-thread accumulator arrays, small LUTs, and scratch buffers. Ships
with a GPU-proven `local_histogram.axc` example (per-invocation 8-bin histogram, bit-exact
vs a CPU oracle on NVIDIA + Lavapipe).

## 2. Syntax — chosen form and justification

### Chosen grammar (exact mirror of `shared`)

```
array hist: array[u32, 8];      // declaration statement
hist[i] = hist[i] + 1u32;        // indexed write (read-modify-write)
let c: u32 = hist[i];            // indexed read
```

Production (mirrors `shared name: shared[elem, N];`):

```
LocalArrayDecl := "array" IDENT ":" "array" "[" ScalarElemType "," IntLit "]" ";"
LocalArrayType := "array" "[" ScalarElemType "," IntLit "]"
```

The keyword **`array`** doubles as (1) the statement introducer and (2) the type-name
keyword — **identically to how `shared` is both introducer and type-name** in
`shared name: shared[elem, N];`.

### Why `array name: array[T, N];` and not `local name: array[T, N];`

| Option | Verdict | Reason |
|---|---|---|
| **`array n: array[T,N];`** (chosen) | ✅ | Exact 1:1 structural mirror of `shared n: shared[T,N];`. **One** new reserved word (`array`). Parser dispatch, AST shape, HIR lowering, and codegen are copy-paste-with-rename from the proven `shared` pipeline — minimal review surface, minimal foot-gun. DESIGN.md §3.1 already names the type `array[T,N]`, so `array` must become a keyword regardless. |
| `local n: array[T,N];` | ✗ | Reads marginally better, but costs a **second** reserved word (`local`) for no grammar benefit and breaks the 1:1 `shared` correspondence that makes the whole milestone mechanical. The storage-class intent is already documented; a keyword is not needed to convey it. |
| `let n: array[T,N];` | ✗ | `let` requires an initializer expression (`let x: f32 = …`); a sized array has no init-expr syntax. Overloading `let` would need a special uninitialized-array form — more grammar, not less. `shared` deliberately did **not** overload `let`; we mirror that. |

**Collision safety (golden-identity):** `array` is not used as a bare identifier in any
existing `examples/*.axc` (verified). The lexer adds a keyword-collision guard for `array`
**mirroring the guard added for `shared` and `local_invocation_id`** — any prior kernel that
used `array` as an identifier would now get a clean parse error (none exist, so
golden-identity is preserved; see AT-2940).

## 3. Semantics table

| Aspect | `array[T, N]` (this milestone) | `shared[T, N]` (M3.2, for contrast) |
|---|---|---|
| **Storage class** | `Function` (per-invocation / thread-private) | `Workgroup` (per-workgroup, shared by all invocations) |
| **OpVariable placement** | **Entry-block prelude** (SPIR-V §2.16.1 — all Function `OpVariable` first in the first block), alongside `let` scalars | Module globals section, **before** `begin_function` |
| **Lifetime / visibility** | Private to one invocation; invisible to other threads | Shared across the workgroup |
| **Declaration** | `array name: array[elem, N];` at **kernel-body top level** (nested decls in `if`/`for`/`while` rejected — §5.1), before first use | `shared name: shared[elem, N];` |
| **Read** | `name[idx]` → `LocalArrayRead` → single-index `OpAccessChain`(Function) + `OpLoad` | `SharedRead` → single-index `OpAccessChain`(Workgroup) + `OpLoad` |
| **Write** | `name[idx] = value;` → `LocalArrayWrite` → `OpAccessChain` + `OpStore` | `SharedWrite` |
| **Index type** | `U32` exactly — no implicit coercion (anti-pattern #1) | `U32` exactly |
| **Element types** | all `ScalarTy` **except `Bool`** (same rule) | all except `Bool` |
| **N** | compile-time **unsuffixed positive integer literal** `1..=cap`; **NOT** a `@strategy` hole | integer literal only (holes unsupported — mirrored) |
| **Value-type on write** | must **exactly** match elem `ScalarTy` (no conversion) | exact match |
| **OOB access** | **UB-by-design** for *symbolic* indices (no bounds check); a *constant* index `≥ N` is a **decidable hard error** (`LocalArrayConstIndexOutOfBounds`, §5.2) | UB-by-design (mirrored) |
| **Initialization** | **Uninitialized** (no `OpVariable` initializer — same as `let` scalars). Read-before-write is **UB**; a decidable **advisory** warning fires (see §5) | Uninitialized; cross-invocation RAW hazard analysis (different hazard) |
| **Cross-invocation hazard** | **None** — private memory needs **no barrier** (the whole `shared` OQ1 missing-barrier analysis is N/A here) | RAW hazard → barrier analysis (hard error + advisory) |
| **Barrier interaction** | none | `workgroup_barrier()` semantics |
| **OpPhi interaction** | **None** — arrays are memory (`OpVariable` + `OpLoad`/`OpStore`), not SSA values. Confirmed: only opaque coopmat SSA accumulators need OpPhi (M3.3); `Function`-storage scalars and arrays never do. | none |
| **New SPIR-V capability** | **None** (Function storage is core Shader). Element-type caps (`Float16`/`Int8`/`Int16`/`Int64`/`Float64`) set **when used**, mirroring `emit_shared_globals` — **no** `StorageBuffer8/16BitAccess` | same element-cap rule |
| **Descriptor / metadata** | **None** — consumes no descriptor, sets no `shared_memory_bytes`, needs no runtime preflight; metadata schema **unchanged (v4, current)** | consumes `shared_memory_bytes`, `maxComputeSharedMemorySize` preflight |
| **Size cap** | aggregate `sum(bytes) ≤ 4096` hard error; spill-advisory `> 1024` (see §6) | aggregate `≤ 65536` bytes; device-limit preflight |

## 4. N is a literal, not a strategy hole (mirrors `shared`)

`shared`'s `parse_shared_len` accepts **only** an unsuffixed positive integer literal;
`@strategy` holes are not accepted for the size operand (the hole enumerator resolves holes
by **source-text substitution before codegen**, but the array size feeds `OpTypeArray`'s
`OpConstant` length operand, which shared does not re-key per candidate). We **mirror this
exactly**: `array[elem, N]` requires an unsuffixed positive integer literal. Hole-sized
local arrays are **deferred** (see §11). Note that a **hole in the index expression**
(`hist[?stride * lane]`) is unaffected — indices are ordinary `U32` expressions and holes
substitute there as everywhere.

## 5. Initialization hazard — the cheaper sound option

A `Function`-storage `OpVariable` has **no initializer** (identical to `let` scalars today,
which are also uninitialized until first assigned). Reading an element before it is written
is **undefined behavior**.

**Why not a mandatory require-write-before-read analysis:** a sound
definite-assignment proof over **symbolic** indices is undecidable — the compiler cannot
prove `hist[j]` was written before `hist[k]` is read for symbolic `j`, `k` without either
false positives or a heavyweight abstract interpreter. This is the same reason `shared`'s
missing-barrier analysis is **SET-based and conservative** (hard error only on a decidable
provable-hazard subset, advisory otherwise).

**Chosen (cheapest sound) rule:** document uninitialized-read as **UB-by-design**, and emit
a **decidable, zero-false-positive advisory** — `HirWarning::LocalArrayReadBeforeAnyWrite` —
fired **only** when a `LocalArrayRead` of array `X` is reached while `X`'s write-set is
**empty** (the array has been declared but **never** written on any path to this read). This
is the exact `shared` write-set machinery, minus the barrier-clearing (private memory has no
barrier): the write-set is populated by every `LocalArrayWrite` and never cleared. This
catches the common foot-gun (forgot to zero the accumulator) with **zero** false positives,
never blocks compilation, and adds ~15 LOC. Per-index definite-assignment is explicitly
**deferred** (it is the undecidable case; matches the `shared` advisory philosophy).

**Honest disclosure — the advisory is path-insensitive (r2, pessimistic LOW #4).** The
write-set is a **source-order presence set**, not a path-sensitive definite-assignment
lattice. It is zero-**false-positive** (it never warns on a genuinely-written array), but it
does **miss true positives**: a write nested inside an `if` (or inside a loop body that runs
zero times) populates the write-set **unconditionally**, so a later read on an *uncovered*
path — the `else` branch, or a post-loop read when the loop was zero-trip — is **not** flagged
even though it reads uninitialized memory. This is the **same conservatism** as `shared`'s
SET-based barrier-hazard analysis (decidable hard subset only, advisory otherwise) and is
accepted for the identical reason: soundness over symbolic paths is undecidable. The advisory
catches the common "forgot to zero it at all" case; it is **not** a correctness guarantee, and
uninitialized-read remains **UB-by-design** on any path.

## 5.1 `array` decls are restricted to kernel-body top level — nested decls REJECTED (r2, pessimistic MEDIUM #2)

**The hazard.** `array name: array[T,N];` is dispatched from the general statement parser
(`parse_shared_decl_stmt` is reachable at `parser.rs:1528`, the same statement parser used
inside `if`/`for`/`while` bodies), so the grammar *would* accept an `array` decl nested inside
control flow. But per SPIR-V §2.16.1 **every** `Function`-storage `OpVariable` is hoisted to
the entry-block prelude with **no initializer** — so an array "declared" inside a `for` loop is
allocated **once** and is **never reset** per iteration. This is a **silent divergence from
`let` intuition**: `let x = expr;` inside a loop re-runs its `OpStore` every iteration; an
`array` decl inside a loop does not. A user writing `for { array scratch: array[f32,4]; /* use
fresh */ }` gets stale cross-iteration state, and the §5 whole-array advisory (write-set
non-empty after iteration 1) will **never** flag it.

**Decision: REJECT nested `array` decls at HIR (option (a)).** An `array` declaration statement
that is not at the **top level of the kernel body block** (i.e. that appears inside any nested
`if`/`else`/`for`/`while` block) is a **hard error** — `HirError::LocalArrayDeclNotAtBlockScope`
— with a clear message: *"local array declarations must appear at the top level of the kernel
body, before any control-flow block; move `<name>` to the top and index it inside the loop."*

**Justification (why (a) over (b) document-hoist-once):**
- **Cheaper.** A single top-level-scope check during lowering (the decl's block nesting depth
  must be 0) is ~10 LOC and needs no per-iteration-reset codegen. Documenting-and-testing
  hoist-once semantics (option (b)) would require a *new* GPU AT proving the surprising
  behavior, and would leave the foot-gun live.
- **Least surprise.** Rejecting the nested form removes the divergence entirely rather than
  asking every reader to internalize it. The array is still fully usable — declared once at
  top, indexed freely inside any loop (the `OpVariable` persists across iterations, exactly the
  intended "per-thread scratch that survives the loop" pattern; §7 OpPhi note, proven by
  AT-2938).
- **Matches the discipline `shared` already has in practice.** Every shipped `shared` decl is
  at body top level; `shared` never *intends* nested-scope reset either. M3.20 makes that
  implicit discipline an **explicit, enforced** rule for the private sibling.
- The histogram example (§10) and every use case (LUT, accumulator, scratch) declares at top
  level already — nothing real is lost.

Enforced in **HIR** (during typecheck/lowering, where block nesting is known), **not** the
parser — the parser still *accepts* the token sequence and produces a `Stmt::LocalArrayDecl` so
it can recover and report other errors in the same pass (anti-pattern #6); the HIR then emits
the scope error. Tested by **AT-2943**.

## 5.2 Provably-out-of-bounds constant index → decidable hard error (r2, pessimistic LOW #3)

OOB access is **UB-by-design** for *dynamic* (symbolic) indices — the compiler cannot decide
`hist[k]` in-bounds for symbolic `k` without a bounds check we deliberately omit (mirrors
`shared`). But a **constant** literal index is **decidable and zero-false-positive**: `hist[8]`
on an `array[u32, 8]` is *provably* out of bounds at compile time (valid indices are `0..=7`).
This is the same cheap-and-sound class as the §5 empty-write-set advisory.

**Rule:** a `LocalArrayRead`/`LocalArrayWrite` whose index is a **constant integer literal `≥ N`**
is a **hard error** — `HirError::LocalArrayConstIndexOutOfBounds` — *not* a warning (a
provably-wrong access should not compile; the `U32` index type already precludes negatives).
**Symbolic** indices remain UB-by-design and documented. ~10 LOC in the index-check path;
catches the common off-by-one the histogram-style RMW pattern invites. Tested by **AT-2944**.

## 6. Size cap — the M3.12 register-pressure lesson

**Honest perf note (must ship in the example header + DESIGN entry):** a `Function`-storage
array that the driver cannot keep in registers **spills to "local memory"** — which on
NVIDIA is off-chip, global-latency, per-thread backing store. The M3.12 ablation diagnostic
established that this kernel class is **register-pressure / occupancy-bound**: live
dequant-chain temporaries alone cut resident warps. A large **private** array is **strictly
more dangerous than `shared`**, because it is replicated **per-thread** (× thousands of
resident threads), not per-workgroup. A naive `array[f32, 4096]` would obliterate occupancy.

**Cap (hard error):** aggregate `sum over all local arrays of total_byte_size ≤ 4096` bytes
→ `HirError::LocalArrayTooLarge` above it. Mirrors `shared`'s aggregate `MAX_SHARED_BYTES`
check in `validate.rs`, but **16× tighter** (4 KB vs 64 KB) because private replication makes
the occupancy cost far higher. 4 KB = e.g. `array[f32, 1024]` or `array[u32, 1024]` — ample
for LUTs / accumulators / small scratch, below the spill cliff on mainstream GPUs.

**Spill advisory (non-blocking):** aggregate `> 1024` bytes →
`HirWarning::LocalArrayMaySpill` (register-file pressure / local-memory spill risk;
consider `shared[T,N]` for workgroup-cooperative data). Decidable, always-safe.

`MAX_LOCAL_ARRAY_BYTES = 4096`, `LOCAL_ARRAY_SPILL_ADVISORY_BYTES = 1024` — new consts in
`crates/axc-hir/src/local.rs`.

## 7. Codegen plan (SPIR-V)

Emitted per declared local array (mirrors `emit_shared_globals`, **Function** storage):

```text
%elem    = <scalar type via ScalarTypeCache>
%n_const = OpConstant %u32 <N>            ; array length is a constant id (SPIR-V 3.32.6)
%arr     = OpTypeArray %elem %n_const     ; SIZED array (not RuntimeArray), one per LocalArrayId
%ptr_fn  = OpTypePointer Function %arr     ; pointer to the whole array (globals/types section)
%ptr_e   = OpTypePointer Function %elem    ; pointer to one element (deduped by rspirv)
; --- and, in the FUNCTION ENTRY-BLOCK PRELUDE (NOT globals) ---
%var     = OpVariable %ptr_fn Function     ; NO initializer; emitted with the let-scalar prelude
```

**Key divergence from `shared`:** the `OpVariable` for a `Function`-storage array **must**
live at the top of the function's first block (SPIR-V §2.16.1 — verified by the existing
`body.rs:509` prelude loop that already emits `let`-scalar `Function` `OpVariable`s and by
the `var_after_non_var` assertion at `body.rs:2532`). So the type triples (`OpTypeArray`,
two `OpTypePointer Function`) are created up front (they land in the module types section via
rspirv dedup), but the **`OpVariable` is inserted in the `body.rs` prelude loop**, right
where `BindingTy::Scalar` variables are created. This is a cleaner fit than `shared` — local
arrays reuse the `let`-scalar Function-variable machinery.

**Read** (`LocalArrayRead { local_array_id, index }`):
```text
%ptr = OpAccessChain %ptr_e %var %idx      ; SINGLE index (no struct-member-0; not the SSBO 2-index form)
%val = OpLoad %elem %ptr
```

**Write** (`LocalArrayWrite { local_array_id, index, value }`):
```text
%ptr = OpAccessChain %ptr_e %var %idx
       OpStore %ptr %value
```

**Capabilities:** none new. `Function` storage is core Shader. Element-type capability flags
(`Float16`, `Int8`, `Int16`, `Int64`, `Float64`) set **when the element type demands it**,
copied verbatim from `emit_shared_globals`'s `match elem_ty` block — because `observe_type`
still does not cover F16 (`body.rs:213` `_ => {}`). **No** `StorageBuffer8/16BitAccess`, no
`SPV_KHR_*_storage` (those gate StorageBuffer class only; Function is a non-StorageBuffer
class, exactly like Workgroup).

**OpPhi:** none. Arrays are memory; no loop-carried SSA. A local array read/written inside a
`for` loop needs **no** OpPhi — the `OpVariable` persists across iterations and
`OpLoad`/`OpStore` see the latest store. Confirmed against M3.3: only opaque coopmat SSA
accumulators require the OpPhi header; scalars and arrays on Function storage never do.

## 8. HIR / typecheck / lowering plan

New module `crates/axc-hir/src/local.rs` (mirror of `shared.rs`):
- `struct LocalArrayId(pub u32)`
- `struct LocalArrayTy { elem: ScalarTy, len: u32 }` with `elem_byte_size`/`total_byte_size`/
  `needs_float16`/`needs_int8`/… (verbatim mirror)
- `struct LocalArrayDecl { id, name, ty, span }`
- `const MAX_LOCAL_ARRAY_BYTES: u64 = 4096`, `const LOCAL_ARRAY_SPILL_ADVISORY_BYTES: u64 = 1024`,
  `const MAX_LOCAL_ARRAY_ELEMS: u32 = 65536` (per-array element ceiling; the byte cap binds first)
- `fn is_allowed_local_element(ty: ScalarTy) -> bool` = `!Bool`

`crates/axc-hir/src/expr.rs`:
- `HirExprKind::LocalArrayRead { local_array_id: u32, index: Box<HirExpr> }`
- `HirStmt::LocalArrayWrite { local_array_id: u32, index: HirExpr, value: HirExpr, span }`
- `HirStmt::LocalArrayDeclMarker { id: LocalArrayId, span }` (preserves source-order; no-op in codegen)
- `KernelBodyTyped.local_arrays: Vec<LocalArrayDecl>` (new field, source order)

`crates/axc-hir/src/typecheck.rs`:
- `local_array_decls: Vec<LocalArrayDecl>` + `local_array_name_map: BTreeMap<String, usize>` +
  `local_array_write_sets: BTreeMap<u32, ()>` (presence = "written at least once")
- `find_local_array(name)`, `register_local_array(name, ty, span)`.
- **Bidirectional, order-independent name-collision cross-check (r2, pessimistic MEDIUM #1 —
  the #1 blocker).** r1 asserted "a name cannot be two of these (collision rejected at
  registration), so order only fixes the read-node kind." **That was UNSUBSTANTIATED and, as
  specified, FALSE.** `register_shared` (`typecheck.rs:812`) checks only `shared_name_map` dup +
  `find_param` + `find_binding` — it knows **nothing** about local arrays. A naive
  `register_local_array` "mirroring `register_shared`" would likewise **not** consult the shared
  map. Result: `shared foo: shared[u32,8]; array foo: array[u32,8];` would be **accepted**, and
  the disambiguation arm (inserted before `find_shared`) would silently resolve **every**
  `foo[i]` to the local array — masking the shared read/write. That is a **real miscompile.**
  **MANDATED FIX (both directions, both declaration orders):**
  1. `register_local_array(name, …)` MUST reject `name` if it is already present in **`shared_name_map`**
     (emit `LocalArrayNameCollision`), in addition to the local-array dup + `find_param` + `find_binding`
     checks it inherits.
  2. `register_shared(name, …)` MUST be **extended** to reject `name` if it is already present in the
     **local-array name map** (emit the collision error), in addition to its existing checks.
  Because both registrars cross-check the other's map, the collision is caught **regardless of
  which decl appears first** in source. Only after this guarantee is *enforced in code* (not
  merely asserted) does the resolution order below reduce to "fixes the read-node kind." Tested
  by **AT-2942**, in **both** declaration orders.
- **Index disambiguation** at `typecheck.rs:2033` (`Expr::Index` with `Ident` base): resolve
  order **local array → shared → buffer**. Given the enforced bidirectional collision guard
  above, a name is at most one of these, so order only fixes the read-node kind. New arm before
  the `find_shared` check:
  ```
  if let Some((id, elem, _len)) = tc.find_local_array(name) { return check_local_array_read(...); }
  ```
- Analogous disambiguation for the assignment target (`name[idx] = …`) → `LocalArrayWrite`.
- `check_local_array_read`: index must be `U32`; result ty = elem; on read, run the empty-write-set
  advisory (§5).
- `check_local_array_write`: index `U32`; value ty **exactly** == elem; populate the write-set.

`crates/axc-hir/src/validate.rs`:
- `LocalArrayZeroLength`, `LocalArrayTooManyElems`, `LocalArrayElementTypeNotAllowed` (Bool),
  `LocalArrayDuplicateName`, `LocalArrayNameCollision` (bidirectional vs shared — §8),
  `LocalArrayAsParameter`, `LocalArrayUndeclared`, `LocalArrayTooLarge` (aggregate byte cap),
  `LocalArrayDeclNotAtBlockScope` (r2, §5.1 — nested decl), `LocalArrayConstIndexOutOfBounds`
  (r2, §5.2 — constant index ≥ N) errors + `LocalArrayReadBeforeAnyWrite`, `LocalArrayMaySpill`
  warnings — mirror the `Shared*` set plus the two r2 additions.
- Aggregate byte-cap check mirroring `validate.rs:507` (`shared` sum).

`crates/axc-hir/src/lower.rs`: add `LocalArrayWrite`/`LocalArrayDeclMarker` to the
statement-scan `None` arms and `LocalArrayRead` to the expr-scan `None` arm (mirror the
`Shared*` arms at `lower.rs:869`/`913` — these are the "does this contain coopmat_mul_add"
scanners; local arrays never do).

## 9. Codegen module plan

New module `crates/axc-codegen/src/local.rs` (mirror of `shared.rs`):
- `struct LocalArrayBindings { var_ids: BTreeMap<u32, Word>, elem_ptr_ids: BTreeMap<u32, Word>,
  arr_ptr_ids: BTreeMap<u32, Word> }`
- `fn emit_local_array_types(b, type_cache, caps, arrays) -> LocalArrayBindings` — emits the
  `OpTypeArray` + both `OpTypePointer Function` per array and sets element caps, **but does NOT
  emit the `OpVariable`** (returns the `arr_ptr` type id so the prelude can create the variable).
- `fn emit_local_array_read(b, bindings, id, index_id, elem_ty) -> Word` — single-index Function
  `OpAccessChain` + `OpLoad` (verbatim mirror of `emit_shared_read`).
- `fn emit_local_array_write(b, bindings, id, index_id, value_id)` — `OpAccessChain` + `OpStore`.

`crates/axc-codegen/src/body.rs`:
- In the entry-block **prelude loop** (`body.rs:509`), after the scalar-binding loop, iterate
  `body.local_arrays` and emit `OpVariable %arr_ptr Function` for each, recording `var_id` into
  `LocalArrayBindings.var_ids`. This is the **only** place a Function-storage OpVariable may go.
- Dispatch `HirStmt::LocalArrayWrite` → `emit_local_array_write`; `HirExprKind::LocalArrayRead`
  → `emit_local_array_read`; `HirStmt::LocalArrayDeclMarker` → `Ok(())` no-op (mirror
  `SharedDeclMarker` at `body.rs:790`).

`crates/axc-codegen/src/emit.rs`:
- Call `emit_local_array_types` in the type-setup phase (parallels the
  `emit_shared_globals` call at `emit.rs:313`) so element caps are registered before
  `begin_function`; thread `LocalArrayBindings` into `KernelResources`.
- Add `LocalArrayRead`/`LocalArrayWrite` arms to the four recursion helpers
  (`expr_uses_gid`, `expr_uses_local_invocation_id`, `expr_uses_subgroup_op`,
  `expr_uses_coopmat`) — recurse into `index`/`value` exactly like the `Shared*` arms at
  `emit.rs:546`/`587`/`638`/etc. (an index may legitimately use `gid()`/`local_invocation_id()`).

**Runtime (`axc-runtime`): NO CHANGE.** No metadata field, no schema bump (stays at the current
`CURRENT_SCHEMA_VERSION = 4`), no preflight. Private memory is not a Vulkan-limited resource we gate at dispatch. This keeps
the change codegen-local and golden-friendly.

**Driver (`axc-driver`): NO CHANGE.** `rewrite_verify`'s `derive_workgroups`-required guard
keys on `shared_memory_bytes > 0 || coopmat`; a purely-local-array kernel sets neither, so it
stays elementwise-1-D derivable (correct — private arrays don't change dispatch geometry).

## 10. Example kernel to ship (GPU-proven value case)

**`examples/local_histogram.axc`** — per-invocation 8-bin histogram. Each invocation owns an
`array hist: array[u32, 8];`, zeroes it, scans its own contiguous slice of an input `u32`
buffer bucketing values `v % 8`, then writes its 8 counts to the output buffer at
`gid*8 + bin`. Bit-exact vs a trivial CPU oracle (`u32` counts → `max_diff == 0`, no
tolerance needed). Runs on **Lavapipe (CI)** and **NVIDIA RTX PRO 6000**.

Why this example: it exercises **every** new surface in one small, obviously-correct kernel —
declaration, zero-init write loop, indexed **read-modify-write** (`hist[b] = hist[b] + 1u32`),
indexed read, `U32` index typing, and the aggregate cap (8×4 = 32 bytes, far under 4 KB). It
is the canonical "per-thread accumulator array" use case named in the value story. Header
carries the §6 spill perf-note.

Secondary use cases documented (not all shipped as kernels): small per-thread **LUTs**,
**prefix-sum scratch**, small-tile **transpose** register staging. A per-thread transpose is
noted as a stretch example but the histogram is the load-bearing GPU proof.

## 13. Defer list

- **Hole-sized arrays** (`array[T, ?n]`) — mirrors `shared`'s literal-only size; the enumerator
  does not re-key `OpTypeArray` per candidate. Deferred.
- **Per-index definite-assignment** (prove `arr[i]` written before `arr[i]` read for symbolic
  `i`) — undecidable in general; only the whole-array-never-written advisory ships (§5).
- **Multi-dimensional / nested arrays** (`array[array[…]]`) — grammar allows only
  `array[scalar, N]`. Deferred.
- **Array-valued `let` / array parameters / array return** — arrays are declaration-statement
  locals only, mirroring `shared`.
- **Automatic bounds checking / clamped indexing** — OOB stays UB-by-design; a future
  `@bounds_checked` annotation could add it (out of scope).
- **Zero-initialization** — arrays ship uninitialized (like `let` scalars); a future
  `array name: array[T,N] = 0;` sugar is deferred.
- **Small-tile transpose / prefix-sum example kernels** — documented as use cases; only the
  histogram ships as the GPU proof.

## 14. Anti-pattern & hard-rule compliance

- **Explicit types** (#1): index must be `U32`, write value must exactly match elem — no
  coercion.
- **No `>>`** (#8): unaffected; array indices use ordinary arithmetic; `shr`/`lshr` unchanged.

- **No feature without a test on a real GPU** (#9 / hard rule): AT-2937/AT-2938 bit-exact on
  Lavapipe + NVIDIA.
- **Annotations first-class** (#4): N/A (no new annotation).
- **50 GB test memory limit**: histogram + fixtures are tiny.

## 15. Forward-compat note — `array` becomes a hard keyword (r2, pessimistic Q4, non-blocking)

Once `array` is a hard keyword it can **no longer be an `@optimization_log` `RecordField` key**:
the field-key parser (`parser.rs:735`) accepts only `TokenKind::Ident` plus the special-cased
`TokenKind::Kernel` (`parser.rs:741`). **No existing `@optimization_log` schema field is named
`array`** (verified — golden-identity holds), so nothing breaks today; this is a *narrowing* of
the future field-key namespace, disclosed here for the record. If `array` is ever wanted as a
field key, add a `kernel`-style parser-local exception (`TokenKind::Array` → treat as the
identifier `"array"` in field-key position) — cheap, isolated, out of scope for M3.20.

The `M3.12` citation in §6 is a **register-pressure analogy**, not a claim that M3.12 measured
`OpTypeArray` byte-size-vs-occupancy: the DESIGN.md §3.1.44 entry cites **general** GPU
register-allocation / local-memory-spill behavior (NVIDIA local-memory spill, AMD scratch/private
model) for the per-thread-replicated spill risk — M3.12 is referenced only for the qualitative
"this kernel class is occupancy-bound" lesson. (r2, optimistic minor.)
