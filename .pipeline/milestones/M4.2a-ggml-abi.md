## 2. The ggml ABI facts (VERIFIED against the pinned SHA, not invented)

All facts re-verified against `vendor/llama.cpp` @ `6b80c74f285390368b3c99c5e750f19e9b096e98` (tag b9542).
Citations are file:line at that SHA.

### 2.1 Buffer bindings — MATCH (zero work)
ggml A=0 / B=1 / D=2 ≡ AXIOM `q`=binding 0 / `x`=binding 1 / `C`=binding 2
(`compute_binding_plan`, buffers in declaration order → binding 0,1,2; `param.rs:55-78`).
Confirmed: dispatch descriptor set is `{ a, b, d }` (`ggml-vulkan.cpp:7863`).

### 2.2 Weight layout — MATCH, bit-exact (the clean win)
`block_q4_K` = 144 bytes (f16 `d`@0, f16 `dmin`@2, 12 B scales, 128 B qs). AXIOM's dequant was built
byte-identical to ggml (`get_scale_min_k4`, 6-bit packed scales) — see `q4km_oracle.rs:63-118` and the
M3.6 kernel lines 154-188. **No dequant arithmetic changes in this milestone.** (Golden: AT-3005.)

### 2.3 Push constants — 17-field struct; AXIOM reads the leading 6 at MATCHING offsets
`struct vk_mat_mat_push_constants` (`ggml-vulkan.cpp:1036-1044`) is **17× u32 = 68 bytes** (r2: full,
correct table — r1 omitted `ne02` and mislabeled the tail):

| off | field | off | field | off | field |
|----:|-------|----:|-------|----:|-------|
| 0  | **M**        | 24 | batch_stride_a    | 48 | **ne02** |
| 4  | **N**        | 28 | batch_stride_b    | 52 | ne12 |
| 8  | **K**        | 32 | batch_stride_d    | 56 | broadcast2 |
| 12 | **stride_a** | 36 | base_work_group_z | 60 | broadcast3 |
| 16 | **stride_b** | 40 | num_batches       | 64 | padded_N |
| 20 | **stride_d** | 44 | k_split           |    |      |

17 fields × 4 B = 68 B. AXIOM lays out scalar push members in **declaration order, std430, 4-byte each**
(`param.rs:80-107`). Declaring the kernel's scalar params as **`M, N, K, stride_a, stride_b, stride_d`**
(after the three buffers) puts them at offsets **0,4,8,12,16,20 — byte-identical to ggml's leading six.**
AXIOM's push block is 24 bytes; the host pipeline layout uses ggml's 68-byte range; the AXIOM shader
reads only `[0,24) ⊆ [0,68)`. Legal (a SPIR-V push block may be smaller than the layout range), COMPUTE
stage, **zero compiler change**. (Golden: AT-2995 — the 17-field literal offset table + bindings.)

### 2.4 `stride_a` UNIT — it is ELEMENTS, so the divisor is **256, not 144** (r1, CONFIRMED)
At the quantized coopmat mul_mm call site, `ggml_vk_matmul(ne01, ne11, ne10, ne10, ne10, stride_d, …)`
(`ggml-vulkan.cpp:8403-8409`), so **`stride_a = ne10 = K in ELEMENTS`** (not bytes). Therefore:

> **`n_blocks_per_row = stride_a / 256u32`** (256 elements per Q4_K superblock), NOT `/144`.

For the contiguous case `stride_a == K`, so `stride_a/256 == K/256`; deriving from `stride_a` is kept
because it is the ABI-designated row stride. (Golden: AT-2988.) The pessimistic reviewer VERIFIED this
from source (`ggml_vk_matmul(ne01,ne11,ne10,ne10,ne10,stride_d,…)`); it stands.

### 2.5 B (activations) — f32 element type, row-major `[N,K]`, staged f32→f16 (r2: CORRECTED)
ggml's `matmul_q4_k_f32` pipeline consumes B as **`float` (f32)** (`vulkan-shaders-gen.cpp:582`
`{"B_TYPE","float"}`), stored row-major with `ne[0]=K` contiguous, `ne[1]=N`: logical element `(k,n)`
lives at `x[n*stride_b + k]` (`stride_b = ne10 = K`). **Two deltas on the B path** (vs the M3.6 leader,
which reads f16 directly at `x[k*N+n]`):
- **element type**: `x: readonly_buffer[f32]`; each element is converted f32→f16 via the existing M3.5
  `f32_to_f16` builtin during B-staging, before writing the (still-f16) `b_tile`;
- **transposed index**: `b_global = b_global_col * stride_b + b_global_row` (ggml `[N,K]` row-major).

The coopmat B operand stays `matrix[f16,16,16,b]` — the canonical f16×f16→f32 HMMA is UNCHANGED; only the
B **source** buffer type + read index change. (Golden: AT-3000 — B elem size == 4 B == ggml B_TYPE.)

### 2.6 D (output) — COLUMN-MAJOR with stride_d (r1, CONFIRMED)
ggml stores D column-major: `coopMatStore(…, gl_CooperativeMatrixLayoutColumnMajor)` at
`(dc+…)*stride_d + dr` (`mul_mm.comp:404`; C++ `stride_d = dst->nb[1]/type_size = M` elements,
`ggml-vulkan.cpp:8175`). AXIOM stores **row-major** `C[row*N+col]`. **The one delta not expressible
today** → §3. (Golden: AT-3003.)

### 2.7 Split-K / batch invariants — the `k_split==1` wording correction (r1, CONFIRMED)
The non-split push (`ggml-vulkan.cpp:7862`) sets the `k_split` FIELD to **`k`** (= K), not 1, for a single
split; only the split-K branch (`:7885`) sets the per-split size. So the correct host precondition is
**`split_k(count) == 1` AND `num_batches == 1`** (the field-value is K in that case). The guard lives in
the **host adapter** (§7.2); the `.axc` kernel ignores fields 6-17 entirely.

### 2.8 Grid axis order — ggml maps x→M-row, y→N-col (r2: NEW, was silently wrong in r1)
`mul_mm.comp:166` `ir = gl_WorkGroupID.x % blocks_m` (`blocks_m = CEIL_DIV(M,BM)`) → **x-axis selects the
M-row block**; `:141` `ic = gl_WorkGroupID.y` → **y-axis selects the N-column block**. The host dispatches
elements `{m, n, groups_z}` (`ggml-vulkan.cpp:7863`), and `ggml_vk_dispatch_pipeline`
(`:7228-7229`) computes `wg0 = CEIL_DIV(M, wg_denoms[0])`, `wg1 = CEIL_DIV(N, wg_denoms[1])`.

The M3.6 leader does the OPPOSITE (`block_col = gid(0)/32` → x=N; `block_row = gid(1)` → y=M). The
variant SWAPS to ggml's convention (§4, delta (e)). **@workgroup implication:** the 32-lane subgroup that
the coopmat requires must stay on the local-x axis, so `@workgroup(32,1,1)` is UNCHANGED; the swap moves
only WHICH global axis feeds `block_row`/`block_col`. The host adapter registers the AXIOM pipeline with
`wg_denoms = {32, 32, 1}` so ggml's `{M,N,z}` dispatch → workgroups `(M/32, N/32, 1)`, local `(32,1,1)`,
`workgroupID.x → M-row` (32 lanes = one subgroup), `workgroupID.y → N-col`. (Golden: AT-3001;
runtime catch: AT-3002 rectangular M=4096,N=512.)

### 2.9 Coopmat pipeline symbol, the SIX-variant aligned family + selection guard (r3: interception mechanism)
On coopmat-KHR NVIDIA, the q4_k f32acc slot `pipeline_dequant_mul_mat_mat[GGML_TYPE_Q4_K].f32acc` is
**SIX pipelines**, not one: the CREATE_MM macro (`ggml-vulkan.cpp:4092-4104`, inside the
`if (device->coopmat_support)` block **`:4090`–`:4211`**) builds `{s,m,l}×{unaligned,aligned}` from **TWO
byte arrays** — `matmul_q4_k_f32_cm1_data[]` (→ the `l`/`m`/`s` slots) and
`matmul_q4_k_f32_aligned_cm1_data[]` (→ the `a_l`/`a_m`/`a_s` slots) — tile size selected by SPEC
CONSTANTS (`l_/m_/s_` wg_denoms + warptile). The Q4_K f32acc registration is `:4135` (via CREATE_MM2 when
`coopmat_acc_f16_support`) or `:4159` (its `else`); **both are INSIDE the coopmat block**. **`:4429` is NOT
coopmat** — it is the `if (device->fp16)` fallback tier (`:4212`+), a separate device class (r2 wrongly
cited it as a coopmat registration). Suffix from `vulkan-shaders-gen.cpp:411` `(coopmat ? "_cm1" : "")`;
`_cm2` is the NV **coopmat2** path (block `:4010`); the scalar `matmul_q4_k_f32_data[]` (no-coopmat) is
never used on coopmat HW.

**Which of the six dispatches on the dominant shape:** on aligned M/N/K, `aligned` is TRUE
(`:8237` `aligned = !quantize_y && ne10==kpad && ne01>8 && ne11>8`), so `ggml_vk_guess_matmul_pipeline`
(`:7796`, tail `:7822-7839`, `return aligned ? mmp->a_l : mmp->l;` etc.) returns the **`a_l`/`a_m`/`a_s`**
aligned variant, the size chosen by M,N.

**Interception mechanism (r3, replaces r2's register-into-slot).** The host patch **overrides the RESULT
of `ggml_vk_guess_matmul_pipeline`** — it reassigns the `pipeline` local right AFTER the call site
(`:8239`), under `#ifdef GGML_VULKAN_AXIOM_Q4K` + the full guard below, to a single **standalone** AXIOM
`_cm1` pipeline. **One interception point covers ALL SIX variants and is alignment-independent** (it does
not matter whether guess returned l/m/s or a_l/a_m/a_s), and is strictly simpler/safer than injecting two
byte arrays into six pipeline slots. The standalone AXIOM pipeline is created with `wg_denoms={32,32,1}`
(§2.8) so ggml's `{M,N,z}` dispatch (`:7863`) maps to `(M/32,N/32,1)` regardless of which variant it
replaced. **Spec-constant / tile-size caveat (honest, NOT gated):** ggml's six variants exist to pick a

## 3. Expressibility verdict + the ONE codegen feature (column-major coopmat_store)

**Verdict: NOT zero-compiler-change.** Five of the six ABI deltas are pure source; the D column-major
store is blocked by a hardcoded layout.

| Delta | Expressible today? | How |
|-------|--------------------|-----|
| (a) `n_blocks_per_row = stride_a/256` | **Yes** | integer div; M3.6 already does `g_k/256u32`. |
| (b) consume ggml's 17-field push (read 6) | **Yes** | declare scalars `M,N,K,stride_a,stride_b,stride_d` → offsets 0..20 (§2.3). |
| (c-B) B **f32**, read transposed, staged f32→f16 | **Yes** | retype `x` to `readonly_buffer[f32]`; `b_tile[ei_b] = f32_to_f16(x[col*stride_b+row])` (M3.5 builtin). |
| (c-D) D stored column-major w/ stride_d | **NO** | `coopmat_store` emits `RowMajorKHR` only (`coopmat.rs:37,238`). |
| (e) grid axis swap (x→M, y→N) | **Yes** | `block_row = gid(0)/32u32; block_col = gid(1);` (§2.8). |

### 3.1 The feature: column-major `coopmat_store` (r1, unchanged)
`CooperativeMatrixLayoutColumnMajorKHR = 1` is a **core `SPV_KHR_cooperative_matrix` layout operand** —
**no new capability**, no new extension. The feature mirrors the existing store VERBATIM except the layout
constant.

**Chosen surface: a new builtin `coopmat_store_col(m, buf, element_offset, stride)`** (4 args, void,
statement-only — identical arity/typing to `coopmat_store`). Rationale for a distinct builtin over an
optional layout argument: (i) keeps `coopmat_store`'s signature and every existing call byte-for-byte
unchanged (zero risk to 30+ existing coopmat tests); (ii) no operator/enum-argument surface; (iii) trivial
parser/typecheck reuse.

Lowering:
- **HIR** (`crates/axc-hir/src/coopmat.rs`): add `CoopMatBuiltin::StoreCol` alongside `Store` (name
  `"coopmat_store_col"`, 4 args, void). Register in the builtin name table (`coopmat.rs:222` area) and the
  `HirStmt::CoopMatStore` path with a `layout: CoopMatStoreLayout` discriminant (`RowMajor`/`ColMajor`).
- **Typecheck** (`crates/axc-hir/src/typecheck.rs:3355 check_coopmat_store_stmt`): reuse verbatim; the
  layout field is orthogonal to typing.
- **Parser** (`crates/axc-parser/src/parser.rs:1817`): `coopmat_store_col` dispatches through the same
  `BuiltinCallStmt` path as `coopmat_store` (void statement).
- **Codegen** (`crates/axc-codegen/src/coopmat.rs`): add `emit_coopmat_store_col_inline` = a byte-copy of
  `emit_coopmat_store_inline` (`coopmat.rs:221`) with the layout `OpConstant` set to **1** instead of
  **0**. `body.rs:885` dispatches on the layout discriminant.

**No shared-memory column-major store** is needed. Only the global-buffer store to `C`/`D` gets the
column-major variant.

### 3.2 Rejected alternative — the operand-swap "compute Cᵀ" trick (r1, unchanged — pessimistic reviewer AFFIRMED)
Compute `Cᵀ = Bᵀ·Aᵀ` by swapping the coopmat operands and staging both tiles transposed; a **row-major**
store with `stride_d` of `Cᵀ` lands ggml's column-major D, bit-identically. **REJECTED**: it is a
mirror-image rewrite of BOTH staging loops, the 2×2 register-block geometry, and the `dsc/dmm` cache
indexing — NOT "VERBATIM except the ABI deltas", it maximizes the M3.6-r1-class silent-miscompile surface,
and makes the bit-exact re-proof far harder to audit. For an opt-in RFC artifact, a 1-operand portable
codegen feature is the lower-risk engineering. (The r1 pessimistic reviewer AFFIRMED this rejection.)

## 5. Oracle + bit-exactness decision

### 5.1 Oracle: a transposing WRAPPER, not a new oracle (r1, unchanged)
The existing `axc_driver::q4km_oracle::q4km_dequant_matmul_f32accum_cpu` computes the **logical** matmul
`y[m,n] = Σ_k dequant(q[m,k])·x[k,n]` in AXIOM's orientation. The ggml variant computes the SAME logical
result. The harness therefore:
1. builds the logical fixtures exactly as the M3.6 tests (`make_q4km_weights`, `make_x_f16` — SAME seed
   scheme, so the cross-kernel bit-identity test reuses them);
2. **transposes only the buffer LAYOUTS** fed to / read from the GPU: pack B as `[N,K]` row-major AND
   **widen f16→f32** for the device (`x_ggml_f32[n*K + k] = f32(x_f16[k*N + n])`, §5.2); read the device D
   column-major (`y_gpu[m*N + n] = D[(n*stride_d + m)]`) back into logical `[M,N]`;
3. calls the **UNCHANGED** oracle on the logical `[M,K]×[K,N]` and compares.

No new numerical code; the single-source-of-truth oracle and its `max_rel_diff_combined` /
`q4km_abs_dot_scale` gate (`q4km_oracle.rs`) are reused verbatim. The wrapper is ~50-70 LOC of pure index
transposition + widen in the test file.

### 5.2 Bit-identity vs combined — decision: **BOTH; bit-identity is primary, gated on an f16-EXACT fixture**
**The r2 coupling (WARNING #8).** The M3.6 leader consumes **f16** B; the ggml variant consumes **f32** B
and converts f32→f16 during staging. Bit-identity between them holds **iff** the f32→f16 convert is
**exact** — i.e. every B value is already f16-representable, so the convert round-trips to the identical
f16 bits the leader loads directly.

**Fixture design (mandatory):** the B activation fixture is generated as **f16 values first** (the
existing `make_x_f16` seeded [-1,1] grid), then **widened to f32** for the ggml variant
(`x_ggml_f32[i] = f32(x_f16[i])`). The `[-1,1]` grid is **finite by construction — it contains no
inf/nan/overflow values** (all magnitudes ≤ 1, well inside f16's normal range, no subnormal-flush
corner), so both the f16→f32 widen and the f32→f16 staging convert are **total and exact** with no
special-value rounding. Widening f16→f32 is exact by construction; the variant's staging
`f32_to_f16` then reproduces the identical f16 bits. ⇒ the coopmat B tiles are bit-identical to the
leader's ⇒ the f32 accumulator receives the identical sequence of f32 adds ⇒ **bit-identity holds** as the
primary anchor. (The weights `q` and the dequant path are untouched; the D store writes identical
accumulator bits to transposed destinations.)

Therefore:
- **Primary gate = cross-kernel BIT-IDENTITY** (AT-1803 discipline): dispatch the M3.6 leader (AXIOM
  layout, f16 B) and the ggml variant (ggml layout, f16-exact f32 B) on the same logical fixture,
  de-transpose the ggml output, assert `max|Δbits| == 0` at K=256/512/14336 (AT-2992/2993/2994). Direct
  detector of any addressing slip, a mis-set `stride_a/256`, a column-major-store bug, an axis-swap error,
  or a non-exact convert.
- **Standing correctness gate = combined condition-aware ≤ FROZEN 1e-3** vs the f32 oracle (via the
  wrapper) at K=256/512/14336 (AT-2989/2990/2991) — retained so that, should bit-identity ever fail,
  correctness is still guarded and the failure is investigated per AT-1803's STOP-and-investigate rule
  BEFORE any tolerance is touched. The 1e-3 is NEVER loosened.

**If the fixture were NOT f16-exact** (arbitrary f32 B), the convert would round and bit-identity would be
**impossible by construction**; the design would then have to drop the bit-identity primary and gate the
variant on combined ≤ 1e-3 alone, with that rationale stated. We AVOID that by designing the fixture
f16-exact — so bit-identity remains the strong anchor. A non-zero diff on an f16-exact fixture is a BUG,
not an accepted numeric difference.

## 10. Edge cases, risks, open questions

**Edge cases**
- `stride_a` unit wrong ⇒ `n_blocks_per_row` wrong ⇒ wildly wrong output — caught by AT-2988 (static
  golden) AND AT-2992-2994 (bit-identity diffs massively). Load-bearing constant.
- B element type wrong (f16 vs f32) ⇒ every B read garbage — caught by AT-3000 (static golden, no HW) AND,
  at runtime, AT-2989-2994 via the widening wrapper.
- Grid axis swap wrong ⇒ transposed tiling / OOB on non-square — caught by AT-3001 (static) AND AT-3002
  (rectangular M=4096,N=512 dispatch).
- Non-exact f32→f16 convert (fixture not f16-exact) ⇒ bit-identity impossible — PREVENTED by the §5.2
  fixture design; a non-zero diff on the f16-exact fixture is a BUG.
- Column-major store off-by-transpose ⇒ AT-2986 (isolated) + AT-2992/3003 catch it.
- `stride_d` alignment: ggml has an aligned/unaligned store split (`mul_mm.comp:395`); AXIOM's
  `coopmat_store_col` uses the generic per-element path (correct for any stride) — no fast-path needed.
- `M%32/N%32/K%256 != 0` or coopmat2 device: host adapter fails closed to stock ggml (§2.9).

**Risks**
1. **The `/256` ABI correction** (§2.4) — VERIFIED by the r1 pessimistic reviewer from source; low risk.
   AT-2988 golden + the Coder re-confirms against `mul_mm.comp` A-indexing.
2. **The codegen feature** expands scope beyond examples/tests. Mitigation: a 1-operand mirror of a
   well-tested emitter; no new capability; AT-2985/2986 isolate it. Fallback = §3.2 (reviewer-affirmed reject).
3. **Silent-miscompile class** (M3.6 r1): NOT reintroduced — the kernel stays VERBATIM (flat single
   K-loop, single-level OpPhi); only addressing / B-type / axis change. Bit-identity (AT-2992-2994) +
   the rectangular AT-3002 are the guards.
4. **coopmat2 scope** (§2.9): on `_cm2` NVIDIA the substitution is inactive. HONESTLY scoped in
   REPRODUCE.md + the RFC; not a defect, a documented coverage boundary.

**Open questions for the design reviewers**
- Q1: Accept the column-major-store **codegen feature** (recommended; r1 pessimistic reviewer AFFIRMED),
  or mandate the §3.2 pure-source operand-swap fallback?
- Q2: `upstream/` at repo root (chosen) vs `docs/upstream/`?
- Q3: Should the guard (§2.9) additionally hard-require `!device->coopmat2` at BUILD time (compile the
  AXIOM path out on coopmat2 devices), or runtime-skip (chosen: runtime fail-closed, so a single build
  serves both device classes)?
